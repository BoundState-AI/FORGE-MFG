# Beth's Architecture Review — SPEC-00 through SPEC-06 (excluding SPEC-03, SPEC-05)

## Strongest Concern: This Spec Suite Is Ready to Build

I'll say it plainly — this is the most complete pre-implementation architecture I've reviewed at BoundState. The module boundaries are clean, the seam contracts are testable, and the dependency direction is enforced at multiple levels. My concerns below are real, but they're refinements, not structural defects.

---

## Strategic Assessment

**Does this serve the business vision?** Yes. The DHF-as-audit-trail positions us for Medtronic without claiming compliance we don't have. SDR-TL-006's non-compliance disclaimer is the right call — I've seen companies lose credibility by over-claiming Part 11. The gap analysis table is honest.

**Does it scale to new domains?** The BSMS mandate (SDR-TL-009) is the right long-term bet. The 9-tool surface is deliberately small, and the extension points (stretch tool placeholders, `IsImplemented` flag, decoration types) are clean. New verticals can add tools without touching the hash chain or session lifecycle.

**Is the abstraction level right?** Almost. A few places are over-specified for hackathon scope, and one place is under-specified. Details below.

---

## SPEC-00 — Orchestration Contract

- **Clean.** Module map, seam definitions, dependency direction, review order — all structurally sound.
- **SDR-TL-009 is the right length.** I know it reads long, but this is the most important architectural decision in the company. Every word earns its place. The enforcement checklist (4 questions) is practical.
- **Minor: ACC table gap.** ACC-08 in SPEC-00 §3 says "Screenshot and feature-tree grounding return valid data" but ACC-08 in SPEC-06 §12 says "Viewer timeline renders a 20-entry session in under 1 second." These are different capabilities with the same ID. **Fix: renumber one of them.** The SPEC-06 ACC-08 should probably be ACC-10 (which is currently "Viewer displays turn timeline from DHF" — related but not identical to the performance criterion).

## SPEC-01 — Wire Protocol

- **The strongest spec in the set.** Polymorphic families are well-defined, hash canonicalization is deterministic, and the test requirements are comprehensive.
- **`decimal` for `FeatureParameterNumber` is the right call.** Floating-point nondeterminism in hash chains is a class of bug that's nearly impossible to debug in production.
- **Concern: `SelectionRef` sort order in `HashCanonicalizer`.** The spec says `PersistentSelectionRef` first, then `SketchSelectionRef`, each sorted by their respective ID fields. But what happens when the same `PersistentId` appears twice with different `DisplayLabel` values? The sort is by `PersistentId` only — if two refs share a `PersistentId` (possible if the same entity is selected twice via different paths), the sort is nondeterministic. **Recommendation:** Add a tiebreaker on `DisplayLabel` (or `DocumentId`) to the sort spec, or assert uniqueness of `PersistentId` within a single `ActiveSelection` list.
- **4 MiB limit is fine for hackathon.** The truncation + `get_feature_tree` fallback is the right 80% solution. Don't build pagination until you have a model that actually exceeds it.
- **`ScreenshotResult.FilePath` co-location constraint is well-documented.** The v2 migration note is exactly the right level of forward-looking — acknowledges the debt without building the bridge.

## SPEC-02 — SolidWorks Adapter

- **Threading model is correct and well-defended.** The `SynchronizationContext` capture, startup probe, reentrancy guard, and two-state cancellation model are all architecturally sound. This is the hardest part of the system to get right, and it reads like someone who's been burned by COM threading before.
- **`ToolCallRegistry` is session-scoped, in-memory only — correct.** The explicit "MUST NOT add persistence" note prevents the most common mistake in this pattern.
- **Concern: `ToolInProgress` flag is a boolean, not a counter.** If a tool handler calls another service method that also dispatches through `ISwCommandQueue` (reentrancy per §2.3), the flag is set/cleared by the outermost `ToolDispatcher` call. But if `EventRelay` fires during a nested reentrant call, `ToolInProgress` is still `true` — correct behavior. However, if someone adds a second `ToolDispatcher`-like entry point in the future, the flag semantics break. **Recommendation:** Add a comment on `ToolInProgress` that it is owned exclusively by `ToolDispatcher` and must not be set/cleared by any other component. Or make it a `private` field with a `ToolDispatcher`-scoped accessor.
- **`AddinSessionIdGenerator` fallback path is well-designed.** The `%LOCALAPPDATA%\.machine-id` fallback for restricted accounts is pragmatic. The `Guid.NewGuid()` nonce guarantees uniqueness regardless of the machine-id source.
- **Minor: `DisconnectHandler` iterating `Queued` entries on disconnect.** The spec says it calls `Cancel()` on each tracker's `CancellationTokenSource`. But the `TaskScheduler`'s queued-cancel behavior is cooperative — if the delegate is already being dequeued by the UI thread at the exact moment of cancel, there's a race. The spec handles this correctly (the task transitions to `Canceled` only if it hasn't started), but the `Abandoned` state for `Executing` calls should also cover the "cancel arrived during dequeue but before execution started" window. **Verify:** the `TaskScheduler.FromCurrentSynchronizationContext()` implementation on .NET Framework 4.8 treats cancel-during-dequeue as `Canceled`, not `RanToCompletion`. If not, this is a Day-0 validation item.

## SPEC-04 — DHF Ledger

- **The hash model is the crown jewel.** Two-level hash coverage (entry + tool_calls_hash), explicit column lists, canonical enum mappings, timestamp normalization — this is the right architecture for a regulated audit trail.
- **SDR-04-008 (cross-workstation hard error) is the correct call.** Silent auto-close was a data-integrity disaster waiting to happen. The structured exception with actionable remediation text is exactly right.
- **Concern: `session_metadata_hash` is deferred.** The spec acknowledges (§3.2) that session metadata is not covered by the entry hash chain, and that a trigger bypass could alter it without invalidating entries. The trigger is defense-in-depth, but the gap is real. **Recommendation for post-hackathon:** Compute `session_metadata_hash` at INSERT time and include it in the first entry's `previous_hash` computation (or a dedicated field). This closes the gap without changing the entry hash model for subsequent entries. For hackathon: the trigger is sufficient. Document the gap in the Medtronic pitch as "known, planned closure."
- **Concern: `DhfEnumMappings` exhaustiveness.** The switch expressions throw `ArgumentOutOfRangeException` for unknown enum values, which is correct. But if someone adds a new `TurnType` variant and forgets to update the mapping, the architecture test catches it only if the test enumerates all enum values. **Verify:** `EnumMappingTests` uses reflection to enumerate all values of each mapped enum and asserts each one round-trips. If it does, this is covered. If it uses hardcoded test cases, it's fragile.
- **`CloseSessionAsync` acquires the per-session advisory lock.** This is the right fix for the close-during-append race. The lock key format (`dhf_append:{sessionId}`) matches between `AppendTurnCore` and `CloseSessionAsync`, which is load-bearing. **Recommendation:** Add a constant or helper for the lock key format to prevent copy-paste divergence.
- **Minor: `OpenOrResumeSessionCore` closes stale sessions on THIS workstation.** The `UPDATE dhf.sessions SET ended_at = NOW() WHERE ended_at IS NULL AND workstation_id = @WorkstationId` closes ALL open sessions on the workstation, not just the one with the matching `addin_session_id`. This is correct for the "lazy cleanup after orchestrator restart" scenario, but it means if two SolidWorks instances are running on the same machine with different `AddinSessionId`s, opening a session for one will close the other's. **Question:** Is this the intended behavior? SPEC-00 §6 says "Two concurrent add-in instances on the same machine produce distinct AddinSessionIds; SPEC-04 must handle the resulting dual-session scenario." The current implementation does NOT handle it — it closes the other session. **This is a spec contradiction.** Either the close-stale logic needs to be scoped to `AND addin_session_id != @NewAddinSessionId`, or SPEC-00 needs to drop the dual-session claim.

## SPEC-06 — Viewer

- **Correctly minimal.** Read-only, isolated DI, no write paths, polling instead of WebSocket push. This is the right 80% viewer.
- **SDR-06-003 enforcement is multi-layered.** Isolated DI container + DI test + architecture test + interface constraint. Four independent mechanisms for one invariant is appropriate for a regulated-adjacent system.
- **SDR-06-006 (non-fatal stretch failures) is the right call.** A misconfigured screenshot path should never prevent the core modeling session from running.
- **Path traversal guards are thorough.** The sibling-directory bypass prevention (trailing `Path.DirectorySeparatorChar` on the normalized root) is a detail most specs miss. Good.
- **Concern: `IReadOnlyDhfRepository` is defined in this spec but owned by SPEC-04.** The interface contract in §3a is detailed enough to implement against, but there's a risk of drift if SPEC-04 changes the return types. **Recommendation:** The interface definition should live in SPEC-04 with a cross-reference from SPEC-06. Currently the spec reads as if SPEC-06 is defining SPEC-04's contract, which inverts the dependency direction. The dependency arrow is SPEC-06 → SPEC-04, so SPEC-04 should own the interface shape.
- **`ValidateChainAsync` cancellation contract is well-specified.** The requirement that the method returns `Truncated=true` instead of throwing `OperationCanceledException` is a good API design decision — it prevents the viewer from needing to distinguish "validation failed" from "validation timed out."

## Cross-Cutting Concerns

### What's Missing

1. **SPEC-03 and SPEC-05 are not in this review.** The seams that touch them (B, C, D, E) are well-defined in SPEC-00, but I can't verify that the lifecycle layer and agent loop honor those contracts without seeing their specs. **This is the highest-risk gap.** SPEC-03 is the most complex module (state machine + timeout + recovery + DHF aggregation), and it's the one most likely to violate seam contracts under pressure.

2. **No observability spec.** Serilog is mentioned in SPEC-06 and `FileLogger` in SPEC-02, but there's no cross-cutting decision about structured logging, correlation IDs, or metrics. For hackathon this is fine. For Medtronic, you need a logging SDR that ensures every DHF-relevant event is traceable from user utterance to DB row. **Recommendation:** Add SDR-TL-010 (Structured Logging) as a post-hackathon item in SPEC-00.

3. **No graceful degradation spec for Anthropic API failures.** SDR-TL-003 locks Opus 4.7 as the primary model, but there's no cross-cutting decision about what happens when the API is unreachable, rate-limited, or returns malformed responses. This probably lives in SPEC-05, but it affects SPEC-03 (lifecycle state for a turn that never got a model response) and SPEC-04 (what DHF entry is written for a failed turn). **Flag for SPEC-05 review.**

### What's Over-Engineered (for hackathon)

1. **`CrossWorkstationSessionConflictException` with `dhf-admin close-session` remediation text.** The exception itself is the right call. The CLI reference in the error message is aspirational — that CLI doesn't exist and won't exist during the hackathon. **Recommendation:** Keep the exception, simplify the message to reference the manual SQL path only. Add the CLI reference when the CLI exists.

2. **Deep validation with integrity-event decorations and atomic deduplication.** This is stretch scope and the spec treats it as such, but the implementation detail (partial unique index on `payload->>'dedupKey'`) is production-grade infrastructure for a feature that may never ship in the hackathon window. **Not a problem** — it's well-scoped as stretch — but don't let it creep into mandatory scope.

### What's Under-Specified

1. **The dual-session scenario (SPEC-00 §6 vs SPEC-04 §6.1).** As noted above, this is a contradiction. Resolve it before implementation starts.

## Verdict

**Ship it.** Fix the dual-session contradiction (SPEC-00 §6 vs SPEC-04 §6.1) and the ACC-08 numbering collision before handing to implementation. Everything else is refinement that can happen during build.

The architecture serves the business vision, maintains the competitive moat (GPTL, evidence-first, negative selection via BSMS), and will still make sense in 6 months. The seam contracts are clean enough that Codex can implement individual modules without understanding the whole system. The 80/20 philosophy is respected — the mandatory scope is achievable, and the stretch scope is well-bounded.

### Fran
1. **[Critical] Cross-spec contradictions will create production defects before code is written**
   - **What’s wrong:** SPEC-00/01/02/04/06 do not agree on several contract details:
     - `AddinSessionId` generation conflicts:
       - SPEC-01 §9 says deterministic from `(machineGuid, swProcessId, loadTimestamp)` with **no fallback** and throws if MachineGuid unreadable.
       - SPEC-02 §8.1 says includes a **Guid nonce** and has a **LOCALAPPDATA fallback machine id**.
     - `AddinSessionId` semantics conflict:
       - SPEC-00 glossary says “UUID generated fresh”
       - SPEC-01 says 32-char lowercase hex hash, not UUID.
     - Handshake message shape conflict:
       - SPEC-02 §6.3 says `AddinReadyMessage` includes `screenshotDir`.
       - SPEC-01 `AddinReadyMessage` has no such field.
     - Error code vocabularies conflict:
       - SPEC-02 uses `"HANDSHAKE_INCOMPLETE"`, `"INVALID_CALL_ID"`, `"EXPIRED_CALL_ID"`, `"TERMINATED_CALL_ID"`, `"INTERNAL_ERROR"`.
       - SPEC-01 enums do not define these values.
       - SPEC-02 also shows uppercase string codes like `"VERSION_MISMATCH"` while SPEC-01 serializes enums as PascalCase.
     - Viewer depends on types not clearly defined in SPEC-04 (`IReadOnlyDhfRepository`, `RepositoryUnavailableException`, `ChainValidationResult`) while SPEC-04 exposes different names/interfaces.
   - **Why this breaks at 3 AM:** Teams will implement to different specs and integration will fail in opaque ways: handshake deserialization failures, stale-epoch false positives, inability to parse protocol errors, viewer startup/runtime failures.
   - **Fix:**
     1. Establish a **single source of truth table** in SPEC-00 for:
        - `AddinSessionId` format and generation ownership
        - handshake message fields
        - protocol error enums
        - shared repository interfaces/exceptions
     2. Update all module specs to reference that canonical table verbatim.
     3. Add a build-breaking **CrossSpecContractSyncTests** project that validates:
        - all enum names match referenced values
        - message DTO fields match spec-required fields
        - shared interface names exist in the owning assemblies
     4. Freeze one `AddinSessionId` algorithm now; do not allow both deterministic and nonce-based variants.

2. **[Critical] Viewer is unauthenticated and localhost-only is not an adequate security control**
   - **What’s wrong:** SPEC-06 explicitly binds to `127.0.0.1:7879` with **no auth** and serves sensitive DHF content including transcripts, screenshots, feature trees, user identities, workstation IDs, and audit metadata.
   - **Why this breaks in production:** “Localhost only” does not protect against:
     - malicious local processes
     - browser-based localhost abuse / CSRF-like attacks from hostile web pages
     - low-privilege malware scraping sensitive medtech/aerospace design data
     - accidental exposure if port forwarding, proxies, or remote support tools are active
   - **Security impact:** OWASP A01 Broken Access Control / A02 Cryptographic Failures / A05 Security Misconfiguration. Also IP exposure risk for proprietary CAD and BoundState process data.
   - **Fix:**
     1. Require a **per-process random auth token** for viewer endpoints, passed via header or signed cookie, even on localhost.
     2. Add `Origin`/`Host` validation and reject cross-origin browser requests by default.
     3. Set explicit anti-clickjacking and anti-sniff headers.
     4. Serve screenshots only behind the same auth gate.
     5. Add a hard “demo mode only” banner if auth remains descoped, because current design is not production-safe.

3. **[Critical] WebSocket bridge on HttpListener with URL ACL is an avoidable local attack surface**
   - **What’s wrong:** SPEC-02 binds `ws://127.0.0.1:7878/bsvoice-cad` with a user-level URL ACL and no stated client authentication.
   - **Why this breaks:** Any local process under the same user context can connect and issue tool calls to SolidWorks unless higher layers reject them. That means arbitrary model mutation, screenshot exfiltration, and audit poisoning.
   - **Fix:**
     1. Add a **mutual session secret** established out-of-band at orchestrator startup and required in the first client message or subprotocol.
     2. Prefer **named pipes** over localhost WebSockets for same-machine IPC if browser compatibility is not required. This significantly reduces accidental exposure.
     3. If WebSocket stays, require:
        - loopback bind only
        - origin/subprotocol validation
        - startup-generated secret
        - connection audit logs with PID if obtainable
     4. Add a threat model note: localhost is not trusted.

4. **[High] Screenshot path handling exposes data and trusts filesystem state too much**
   - **What’s wrong:** Screenshots are written to shared disk and referenced by absolute path. Viewer serves them later. Integrity is checked by hash, but confidentiality and access lifetime are weakly controlled.
   - **Failure modes:**
     - stale screenshots left on disk beyond intended retention
     - other local processes reading images directly from `%LOCALAPPDATA%\BSVoiceCAD\screenshots`
     - path leakage in DHF exposing machine usernames/home paths
     - screenshot file replacement or deletion causing inconsistent audit views
   - **Fix:**
     1. Do not store raw absolute paths in DHF long-term; store a **logical artifact ID** plus relative path.
     2. Apply restrictive ACLs on screenshot directories and explicitly document them.
     3. Add max file size and image validation before ingestion/serving.
     4. Consider encrypting screenshots at rest if regulatory/demo sensitivity matters.
     5. Log and surface screenshot integrity failures, but also classify whether the file became unreadable due to cleanup vs tamper.

5. **[High] Session-closing behavior in SPEC-04 can silently close legitimate sessions on same workstation**
   - **What’s wrong:** `OpenOrResumeSessionCore` closes **any stale open sessions on the workstation** before opening a new one.
   - **Why this breaks:** Same workstation can plausibly run:
     - multiple orchestrator instances accidentally
     - multiple users via remoting
     - test/dev concurrent sessions
     - race conditions during restart
     This logic can close unrelated or still-recoverable sessions without operator intent.
   - **Fix:**
     1. Scope closure more narrowly: close only sessions for the same workstation **and same user identity**, and ideally same app instance class.
     2. Record a specific closure reason, not just implicit `ended_at`.
     3. Add an operator-visible warning when stale sessions are auto-closed.
     4. Introduce a lease/heartbeat field on sessions so “stale” is evidence-based, not inferred solely by workstation collision.

6. **[High] DHF chain does not anchor session metadata cryptographically**
   - **What’s wrong:** SPEC-04 admits session metadata is only trigger-protected, not chain-hashed.
   - **Why this matters:** User identity, workstation ID, software versions, and protocol version are provenance-critical. If those fields are altered by a privileged DB user or trigger bypass, the chain still validates.
   - **Compliance concern:** This weakens audit provenance and undermines claims aligned with SWE-013/032/033-style traceability and data integrity expectations.
   - **Fix:**
     1. Add `session_metadata_hash` computed at session creation.
     2. Include that hash in the first entry or in all entry hash inputs.
     3. Add repository/reporting that exposes metadata-hash verification status.
     4. Separate DB roles post-hackathon so app cannot drop protective triggers.

7. **[High] Protocol error handling is underspecified for malformed/unparseable JSON**
   - **What’s wrong:** You define envelope validation and unknown message handling, but not the behavior for:
     - invalid JSON syntax
     - missing discriminator property
     - duplicate keys
     - huge nested structures intended to exhaust memory/CPU
   - **Why this breaks:** Real-world malformed inputs won’t deserialize into typed records. “Send protocol error message” is impossible if the parser is already in an undefined state unless raw-edge handling is specified.
   - **Fix:**
     1. Define a raw receive pipeline:
        - size limit
        - UTF-8 validation
        - parse with duplicate-key detection policy
        - discriminator extraction from raw DOM
        - only then typed deserialize
     2. Specify behavior for parse failure: log sanitized summary, send generic malformed message if connection still usable, optionally close on repeated offenses.
     3. Add fuzz/property tests for malformed payloads and JSON bombs.

8. **[High] AddinSessionId and CallId validation is inconsistent and may cause replay/forgery issues**
   - **What’s wrong:**
     - `AddinSessionId` is top-level epoch authority, but no authenticity guarantee exists.
     - `CallId` duplicate replay is cached for 60 seconds only.
     - Completed results can be replayed on reconnect by resubmitting same CallId.
   - **Why this breaks:** A malicious local client can replay prior calls/results semantics, confuse lifecycle correlation, or intentionally poison DHF with expected-yet-malicious resubmits.
   - **Fix:**
     1. Bind the connection to an authenticated client identity/secret.
     2. Add a **connection/session nonce** into message validation.
     3. Document replay policy explicitly and log every replayed `Completed` result.
     4. Consider extending cache semantics to distinguish benign reconnect replay from suspicious replay volume.

9. **[High] Deep validation can produce misleading conclusions under retention cleanup**
   - **What’s wrong:** Missing screenshot files are warnings, not failures, because cleanup is expected.
   - **Why this breaks:** For an audit log, “we can no longer verify the screenshot artifact” is not nothing. In regulated or forensic contexts, that’s degraded evidence.
   - **Fix:**
     1. Split validation outcome into:
        - `Valid`
        - `Tampered`
        - `EvidenceUnavailable`
     2. Preserve explicit retention policy metadata in the DHF/session.
     3. Viewer should not show “valid” if evidence is missing; show “chain valid, artifacts partially unverifiable.”
     4. Consider immutable artifact storage for production.

10. **[High] No explicit redaction/data minimization strategy for transcripts, screenshots, and feature trees**
    - **What’s wrong:** Raw transcript is authoritative and preserved verbatim. Screenshots and feature trees may contain proprietary geometry, filenames, customer names, part numbers, or regulated product details.
    - **IP/compliance risk:** This is a major data exposure vector, especially if logs are demoed, exported, or copied. It also risks exposing proprietary BoundState operating assumptions in customer-facing artifacts.
    - **Fix:**
      1. Classify fields by sensitivity: public/demo/internal/customer-confidential/regulatory.
      2. Add viewer/export redaction mode.
      3. Ensure logs never dump full transcript/result payloads by default.
      4. Add explicit “do not include raw screenshots in public demo exports unless approved” rule.

11. **[Medium] Session and entry reads may leak inconsistent state to viewer**
    - **What’s wrong:** SPEC-06 accepts eventual consistency, but page rendering depends on multiple separate repository calls.
    - **Why this matters:** Operators may see:
      - header says 7 entries, list shows 8
      - shallow validation for one prefix while list includes a later entry
      - “hash chain valid” while an in-flight append is mid-commit in another call
    - **Fix:**
      1. Add a repository method that returns **session summary + entries + shallow validation** in one snapshot transaction for page load.
      2. Mark UI values as “live / may update” if using polling-based eventual consistency.
      3. Include `asOfTimestamp` in API responses.

12. **[Medium] Advisory-lock design uses `hashtext`, which is collision-prone**
    - **What’s wrong:** Postgres `hashtext` is not collision-resistant enough for lock namespace design.
    - **Why this breaks:** Rare but real lock aliasing could serialize unrelated sessions or, worse, fail to isolate intended ones if lock keys collide in ways you didn’t expect.
    - **Fix:**
      1. Use the two-int advisory lock form with a stable namespace constant + parsed GUID-derived int pair.
      2. Or use a 64-bit hash with documented collision analysis.
      3. Add tests ensuring lock key derivation is deterministic and namespaced by entity type.

13. **[Medium] Tool result semantics after timeout remain operationally dangerous**
    - **What’s wrong:** You correctly admit timed-out COM calls may still mutate the model. Recovery is mandatory. Good. But the spec still leaves dangerous ambiguity:
      - what if recovery event append fails?
      - what if state refresh succeeds but undo rollback also partially applies?
      - what if user manually edits model before reconciliation on reconnect?
    - **Why this breaks:** Data integrity and operator trust collapse when the system says “timed out” but geometry changed.
    - **Fix:**
      1. Define a strict operational order:
         - detect timeout
         - hard-lock new turns
         - attempt recovery
         - append recovery event
         - if append fails, remain locked and surface fatal audit persistence error
      2. Record a model-state fingerprint before and after recovery.
      3. Require manual acknowledgment for unlock after ambiguous recovery.
      4. Add explicit acceptance tests for “timeout + late completion + append failure”.

14. **[Medium] `HttpListener` and WinForms SynchronizationContext are brittle platform choices**
    - **What’s wrong:** Both are expedient, but brittle under environment variation, corporate endpoint controls, and future supportability.
    - **Why this breaks:** You are coupling critical behavior to implementation details that may vary across SolidWorks versions and Windows configurations.
    - **Fix:**
      1. Mark both as **hackathon implementation choices**, not architectural truths.
      2. Add contingency design notes:
         - alternative IPC transport
         - alternative UI-thread marshalling mechanism if `SynchronizationContext` assumptions fail
      3. Monitor startup probe failures as a first-class operational metric.

15. **[Medium] Logging guidance is insufficiently privacy-safe and operationally structured**

    - **Why this breaks:** Stack traces and exception messages can contain:

      - transcript fragments
      - customer design names

    - **Fix:**

      2. Redact transcript/screenshot paths by default in info/warn logs.
      3. Correlate all logs with `AddinSessionId`, `SessionId`, `CallId`, `UndoGroupId`.
      4. Rotate and ACL-protect log files.
      5. Add “safe diagnostic bundle” vs “full debug mode” separation.

Issue → SPEC-04 contradicts SPEC-00 on dual add-in sessions per workstation  
Why it matters → This is the most important unresolved architectural contradiction. SPEC-00 explicitly says:
- two concurrent add-in instances on the same machine produce distinct `AddinSessionId`s
- SPEC-04 must handle the resulting dual-session scenario

But SPEC-04 `OpenOrResumeSessionCore` does:

```sql
UPDATE dhf.sessions
SET ended_at = NOW()
WHERE ended_at IS NULL
  AND workstation_id = @WorkstationId
```

That closes all open sessions for the workstation, including legitimate concurrent sessions with different `addin_session_id`s. This is not a corner case; it is a direct violation of the glossary contract.

Suggested fix → Close only stale sessions that are proven superseded, not every open session on the workstation.

Minimum fix:

```sql
UPDATE dhf.sessions
SET ended_at = NOW()
WHERE ended_at IS NULL
  AND workstation_id = @WorkstationId
  AND addin_session_id = @SupersededAddinSessionId
```

Better: introduce an explicit close path keyed by session, not workstation sweep logic.

```csharp
// Resume same addin_session_id on same workstation
if (existing is { WorkstationId: var ws } && ws == metadata.WorkstationId)
    return existing.SessionId;

// Only open new session; do not mass-close other open sessions for same workstation
await conn.ExecuteAsync(
    @"INSERT INTO dhf.sessions (...) VALUES (...)",
    args, tx);
```

If you really need cleanup for orphan sessions, base it on heartbeat age or explicit closure reason, not workstation collision alone.

Issue → Session closure semantics are still inconsistent across specs

Overall assessment → The decomposition is strong; the remaining defects are contract-level, not module-boundary-level  
Why it matters → I agree with prior reviewers that the six-module split is clean:
- Protocol as leaf module is correct
- Adapter/lifecycle separation is correct
- DHF as sole writer is correct
- Viewer read-only dependency is correct

The real problem is not abstraction choice; it is unresolved ownership and drift at the seams. Until those are collapsed into single-source contracts, implementation will fork.

Suggested fix → Before coding:
1. Resolve `AddinSessionId` ownership and wording everywhere
2. Resolve protocol error enums
3. Resolve `AddinReadyMessage` shape
4. Resolve session close/resume semantics
5. Move viewer read contracts into SPEC-04 ownership
6. Fix the dual-session contradiction in SPEC-04
7. Add cross-spec sync tests

If those are fixed, the architecture is implementation-ready. If not, teams will “successfully” build incompatible modules.
